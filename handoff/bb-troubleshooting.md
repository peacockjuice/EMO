# EMO: диагностика BB и защита от повторных ошибок

Практические выводы из восстановления сети и обновления OLED 2026-11-17. Актуальный выпуск и поведение экрана описаны в родительской спецификации; отчёты ниже относятся к конкретным этапам, а не автоматически к последней сборке.

## Память: что измерять

На ESP32 `gc.mem_free()` учитывает крупнейший native-блок, доступный для расширения Python heap. Большое значение не означает достаточный запас памяти Wi-Fi. Сопоставлять `micropython.mem_info()` с `esp32.idf_heap_info(esp32.HEAP_DATA)`: каждый tuple содержит total/free/largest/minimum free. Сумма свободной памяти нескольких пулов в подписанном `native_heap` и максимальный `native_largest` не равны запасу одного Wi-Fi-пула. [Справочник MicroPython](https://docs.micropython.org/en/latest/library/esp32.html).

Импорт прежнего монолитного emo_bb уменьшал основной native-пул с 35 548 до 728 байт при обманчиво высоком gc.mem_free(). После разделения состояния, HTTP и renderer изолированные импорты сохраняли 34 116 байт. См. [исходное измерение](../preview/bb-memory-diagnosis.json) и [разделённые модули](../preview/bb-memory-after.json). Размер исходника не заменяет измерение пика компиляции и числа создаваемых объектов.

В новом цикле сохранять следующие ограничения:

- При старте bmo.main применяет начальный режим BB через set_mood; bmo.set_mood при выборе BB загружает HTTP-приёмник; затем emo_bb.run загружает emo_bb_view, шрифт и renderer по отдельности, с gc.collect между импортами. Не полагаться на случайный ранний heartbeat в режиме auto. Это функциональная зависимость, а не косметический порядок imports.
- Шрифт остаётся упакованной таблицей 460 байт. Восстановление словаря глифов из этой таблицы снова создаёт долгоживущие объекты.
- Renderer использует уже загруженные штатные последовательности без сдвига и без счётчиков во время лица; не подгружать вторую карту компактных последовательностей.
- Не объединять модули обратно. После добавления сценариев 2026-11-18 модуль renderer снова пришлось разделить: emo_bb_view.py считает фазы, emo_bb_display.py рисует. После этого запуск BB без предварительного heartbeat восстановился; точный пик выделений без USB не измерен. Один gc.collect не исправляет уже отданную Python heap native-память.

Изолированный импорт по USB проходил и у вариантов, терявших сеть при обычном запуске. REPL останавливает приложение и меняет порядок выделений; его успех не является приёмкой запуска. Отдельный прогон рисования 100 кадров не выявил утечки, но не проверял конкуренцию с сетью. Попытки ранней загрузки всех модулей, дополнительного дробления и одной оптимизации рисования не дали достаточного доказательства исправления. Причина каждого trial-отката отдельно не установлена.

## HTTP: задержка не всегда означает потерю Wi-Fi

Чтение сокета по одному байту уступает управление на каждом байте. При частой перерисовке это задерживало заголовки и подтверждения даже после исправления памяти. emo_http.Buffered читает ограниченными порциями по 128 байт и сохраняет остаток тела, прочитанный вместе с заголовками. Не заменять это неограниченным read и не отбрасывать остаток.

Сохранять единый срок ожидания на все заголовки и ограничения длины/числа строк и тела. Nonce повторно проверяется после awaited чтения тела: без этого перекрывающиеся запросы могут использовать его повторно. Ручной выбор режима должен побеждать поздний пакет.

Проверка таймаута должна доказывать достижение нужного участка. Во время правок локальный import gc затенил переменную и вызвал исключение раньше writer.drain, а тест закрытия сокета оставался зелёным. Исправленный тест проверяет и сам вызов drain. Проверять причину успеха теста, а не только итоговый зелёный статус.

## Порядок диагностики и обновления

1. Сохранить режим и инверсию, проверить доступность панели и состояние источника/доставки плагина отдельно. Источник unknown при живом HTTP не означает, что данные сессий актуальны.
2. Перед OTA остановить отправителя и выбрать auto. Применять только полный bundle по процедуре Wi-Fi updater. Не перепрошивать вслепую при каждом сетевом таймауте.
3. После таймаута клиента сначала прочитать OTA status: прерывание клиента не отменяет staged upload. Разобраться с pending через штатный updater, затем повторять операцию. Не писать отдельные файлы в слот.
4. Успех установки: local release = active = running, pending отсутствует, trial false, результат confirmed. Release hash — хеш манифеста приложения, не Git commit SHA.
5. Если нужна USB-диагностика, заново найти последовательный порт: суффикс меняется после переподключения. Остановить отправителя. tools/check_bb_memory_board.py PORT измеряет импорты и сбрасывает плату; это прерывающая приложение операция.
6. После raw REPL всегда reset в finally, включая ошибки; затем восстановить режим/инверсию. Не читать wifi_cfg.py, ap_cfg.py или ключи; не сохранять в Git сырые UART-логи, которые могут содержать SSID.
7. Проверить обычный старт: чистый reset, убедиться, что BB выбран автоматически без команды /set, затем включить плагин. Так проверяется худший порядок без предварительного прогрева HTTP через heartbeat. Дождаться sourceReady и live на обеих сторонах до старта нагрузочной проверки.

## Повторяемая приёмка

Работать из /Users/vpavlin/projects/EMO, а не из старого снимка thread-storage. Локально:

```sh
rtk proxy python3 tools/check_bb.py
rtk proxy npm --prefix bb-plugin-emo test
rtk proxy npm --prefix bb-plugin-emo run check
rtk proxy node tools/check_web.mjs
```

После изменений прошивки и её подтверждённой установки запустить при уже работающем BB:

```sh
rtk proxy python3 tools/check_bb_live.py --url http://192.168.1.43 --rounds 12 --interval 6 --report preview/bb-cycle-acceptance.json
```

Адрес проверить перед запуском: DHCP может его изменить. Скрипт сравнивает полный HTML и Content-Length, проверяет live у платы и отправителя, рост кадров и подтверждённых seq при неизменном epoch. Не запускать параллельно с перезагрузкой, OTA или ещё не завершившимся ожиданием готовности. После чистого старта повторить минимум три раунда с интервалом, позволяющим пройти heartbeat. Отчёт не должен заменять оптическую проверку OLED. При новом выпуске обновить ссылки/хеши в спецификации и явно отделить старые свидетельства.
